# Git Summary

Git 변경사항, fetch 결과, diff, commit 내용, 작업 내용을 프로젝트 템플릿 형식으로 정리한다.

## 사용 시점
다음 요청이 있으면 이 스킬을 사용한다.

- `git fetch 템플릿으로 정리`
- `git featch 템플릿으로 정리`
- `git summary`
- `git-summary`
- `변경사항 이슈 템플릿으로 정리`
- `커밋 내용을 이슈 형식으로 정리`
- `버그 템플릿으로 정리`
- `버그 수정 템플릿`
- `bug template`
- `bug summary`
- `리팩토링 템플릿으로 정리`
- `리펙토링 템플릿으로 정리`
- `refactor summary`
- `refactor 템플릿`

## 절차
1. 사용자가 제공한 git 출력, diff, commit, 작업 내용을 읽는다.
2. 내용이 없고 저장소 접근이 가능하면 필요한 git 정보를 확인한다.
3. 기능 추가, 버그 수정, 삭제, 설정 변경, 문서 변경, 리팩터링을 구분한다.
4. 요청 의도에 맞는 템플릿을 선택한다.
5. 선택한 템플릿 형식으로 한국어 요약을 작성한다.
6. TODO는 실제 후속 작업 또는 확인 항목으로 바꾼다.
7. 정보가 부족한 항목은 지어내지 말고 `확인 필요`로 표시한다.

## 템플릿 선택
- 기능 추가, 작업 이슈 정리: `assets/issue-template.md`
- 버그 재현/버그 수정 정리: `assets/bug-template.md`
- 코드 구조 개선, 가독성 개선, 중복 제거, 성능 개선, 네트워크 요청 감소, 리팩터링 정리: `assets/refactor-template.md`

## 이슈 출력 템플릿
```md
## 📄 이슈 내용

## 📝 상세 내용

<!--- 기능 추가와 관련된 상세 내용을 작성해 주세요. -->

## ✅ 체크리스트

- [ ] TODO A
- [ ] TODO B
- [ ] TODO C
```

## 리팩터링 출력 템플릿

```md
## ✅ 리펙토링 결과
```


## 작성 규칙
- 제목 없이 선택한 템플릿 본문만 출력한다.
- 요청이 버그 또는 버그 수정이면 버그 템플릿을 사용한다.
- 요청이 리팩터링이면 리팩터링 템플릿을 사용한다.
- 요청이 일반 이슈 정리이면 이슈 템플릿을 사용한다.
- `이슈 내용`은 한두 문장으로 요약한다.
- `상세 내용`은 변경 이유와 사용자 영향 중심으로 작성한다.
- 버그 템플릿의 `Given`, `When`, `Then`은 재현 조건, 사용자 행동, 실제 문제를 기준으로 작성한다.
- `버그 수정 결과`는 수정 후 기대 동작과 확인 결과를 작성한다.
- `코드 리펙토링 내용`은 어떤 구조/코드를 어떻게 바꿨는지 작성한다.
- `리펙토링 결과`는 가독성, 유지보수성, 성능, 요청 수, 중복 제거 등 확인 가능한 변화 중심으로 작성한다.
- 체크리스트는 검증 가능한 항목으로 작성한다.
- 테스트, 빌드, 린트 결과가 있으면 체크리스트 또는 결과에 포함한다.
- 불확실한 내용은 단정하지 않는다.
