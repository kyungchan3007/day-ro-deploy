# AI Workflow Performance Guidelines

## 목적

> Next.js 프론트엔드 프로젝트에서 성능 최적화를 진행할 때
> 점수 중심의 잘못된 작업 순서, 과한 리팩토링, 불필요한 사이드 이펙트를 줄이기 위한 실행 지침

## 1. 기본 원칙

- 성능 점수보다 실제 병목 원인 식별 우선
- Lighthouse 진단 항목과 Core Web Vitals를 같은 우선순위로 취급 금지
- 숫자만 보고 수정 시작 금지
- `LCP attribution` 없이 이미지, CSS, JS 최적화부터 시작 금지
- 전역 레이아웃, Provider, 전역 상태 경계 변경은 마지막 단계로 미룸
- 성능 개선 작업은 항상 `낮은 위험 → 높은 위험` 순서로 진행

## 2. 우선 확인 순서

### 2-1. 첫 단계

1. 측정 환경 고정
2. 대상 페이지 고정
3. 모바일/데스크톱 분리 측정
4. Lab 데이터와 실제 브라우저 측정 분리

### 2-2. 반드시 먼저 볼 항목

1. `LCP`
2. `LCP attribution`
3. `INP`
4. `CLS`
5. `TTFB`

### 2-3. 해석 규칙

- `LCP`가 이미지인지 텍스트인지 먼저 확인
- `LCP`가 텍스트면 이미지 최적화부터 하지 않음
- `LCP`가 이미지면 `loading`, `fetchpriority`, `preload`, 실제 파일 크기부터 확인
- `LCP` 수치가 이미 매우 낮으면 점수보다 다른 병목으로 이동
- `unused CSS`, `unused JS`는 진단 항목이지 바로 1순위 작업 아님

## 3. 측정 절차

### 3-1. 권장 측정 흐름

1. `PageSpeed Insights` 또는 Lighthouse로 대상 페이지 측정
2. 브라우저에서 `web-vitals attribution` 확인
3. 콘솔/로컬 수집값으로 실제 LCP element 확인
4. 해당 element를 만든 컴포넌트 추적
5. 그 컴포넌트가 서버 컴포넌트인지 클라이언트 컴포넌트인지 확인
6. 이미지 병목인지 렌더 병목인지 분류

### 3-2. 금지 패턴

- `unused CSS` 수치만 보고 전역 CSS부터 대규모 삭제
- `unused JS` 수치만 보고 Provider 구조부터 변경
- 점수 1회 측정만으로 구조 개편 결정
- attribution 없이 "히어로 이미지가 문제일 것"이라고 가정

## 4. 병목 분류 기준

### 4-1. 이미지 병목

다음 중 2개 이상이면 이미지 병목으로 분류

- `LCP element`가 이미지
- `LCP attribution.url` 존재
- 전송 크기가 비정상적으로 큼
- `resourceLoadDuration`이 큼
- `fetchpriority=high` 또는 preload 미적용

### 4-2. 렌더 병목

다음 중 2개 이상이면 렌더 병목으로 분류

- `LCP element`가 텍스트 블록
- `elementRenderDelay`가 큼
- 조건부 렌더링 또는 hydration 이후 표시
- `use client` 컴포넌트 경계 아래에서 첫 화면 콘텐츠가 렌더됨
- 애니메이션, 탭, 아코디언, skeleton 교체 후 본문 표시

### 4-3. 공용 번들 병목

다음 중 2개 이상이면 공용 레이아웃 병목으로 분류

- 여러 페이지에서 동일 JS 청크가 반복적으로 first load에 포함
- 홈 전용 최적화를 해도 unused JS가 크게 유지
- `app/layout`, `(main)/layout` 아래 클라이언트 경계가 큼
- `GlobalNav`, `Notification`, `Toaster`, `Providers`가 모든 라우트에 선로딩

## 5. 작업 우선순위

### 5-1. 1순위: 로우 리스크

- LCP 이미지 파일 크기 축소
- WebP/AVIF 전환
- `loading=lazy` 제거, `fetchpriority=high` 조정
- 전역 CSS에 섞인 페이지 전용 규칙을 로컬 컴포넌트로 이동
- 첫 화면 아래 영역의 `content-visibility` 적용 검토
- 홈 전용 무거운 클라이언트 슬롯 동적 import 검토

### 5-2. 2순위: 미들 리스크

- 광고 스크립트 전역 주입 제거 후 슬롯 시점 로드
- 알림 벨, 비핵심 상호작용 UI 지연 로드
- 폰트 preload 전략 조정
- 특정 페이지에서만 필요한 클라이언트 컴포넌트 경계 축소

### 5-3. 3순위: 하이 리스크

- React Query Provider 범위 변경
- 전역 레이아웃의 클라이언트 경계 해체
- 전역 토스트/알림/인증 UI 마운트 구조 변경
- 라우트 그룹 단위 CSS/JS 번들 구조 재설계

## 6. CSS 최적화 지침

### 6-1. 먼저 할 것

- `globals.css`에 남은 페이지 전용 클래스 제거
- 특정 화면에서만 쓰는 장식 스타일은 해당 컴포넌트로 이동
- 홈 첫 화면과 무관한 스타일이 전역에 있는지 확인

### 6-2. 나중에 할 것

- Tailwind 유틸리티 총량 자체를 문제로 간주한 대규모 구조 변경
- 폰트 로딩 전략 변경
- 앱 전체 CSS 번들 분해

### 6-3. 해석 규칙

- Lighthouse의 `unused CSS`는 폰트 선언, 반응형 클래스, hover/focus 규칙도 함께 포함할 수 있음
- CSS 수치가 크더라도 실제로는 전역 공용 청크 구조 문제일 수 있음
- 기능 영향 없는 소규모 정리와 구조 변경성 작업을 구분

## 7. JS 최적화 지침

### 7-1. 먼저 할 것

- 첫 화면 바로 아래 비핵심 클라이언트 컴포넌트 dynamic import
- 사용자 상호작용 전까지 필요 없는 UI 지연 로드
- 광고/분석/보조 위젯 전역 주입 제거 검토

### 7-2. 나중에 할 것

- `Providers` 범위 축소
- `GlobalNavClient` 구조 분해
- `NotificationBell` 상태 관리 구조 변경
- 인증 복구 흐름 컴포넌트 전역 구조 변경

### 7-3. 해석 규칙

- `unused JS`는 클릭 전 코드, hover 전 코드, 다른 라우트 공용 코드도 포함
- 특정 청크 하나만 보고 특정 컴포넌트가 원인이라고 단정 금지
- build manifest, route bundle stats, dynamic import 결과를 함께 확인

## 8. 레이아웃/전역 구조 변경 규칙

- 전역 레이아웃 수정 전 반드시 영향 범위 문서화
- `Provider`, `Toaster`, `GlobalNav`, `Notification`은 전역 책임이 있으므로 마지막 순서
- 성능 개선을 위해 전역 구조를 건드릴 때는 기능 회귀 가능성을 먼저 명시
- "성능 개선"만을 이유로 인증 흐름, 캐시 범위, 알림 동작 변경 금지

## 9. 검증 규칙

### 9-1. 최소 검증

- 타입체크
- 대상 페이지 수동 측정 재실행
- LCP attribution 재확인

### 9-2. 구조 변경 시 필수 검증

- 관련 E2E 실행
- 데스크톱/모바일 각각 확인
- 로그인/비로그인 상태 각각 확인
- 주요 CTA 이동 확인

### 9-3. 전역 구조 변경 시 추가 검증

- 알림
- 토스트
- 보호 라우트
- 인증 복구
- 하단 네비/상단 헤더

## 10. 실무 운영 방식

- 성능 측정용 브랜치는 별도 사용 가능
- 프로덕션 배포 전용 코드와 측정 보조 코드는 분리
- 임시 `web-vitals` 로깅 코드는 기능 브랜치에 오래 남기지 않음
- 측정 코드는 `env flag`로만 켜고 끌 수 있게 구성
- 결과 공유 시 숫자보다 `원인 요소`, `변경 리스크`, `검증 결과`를 함께 기록

## 11. AI 작업 지시 템플릿

### 11-1. 분석 요청 템플릿

> 대상 페이지의 성능을 분석하되 점수 요약보다 실제 병목 원인 식별을 우선
> 먼저 `LCP attribution` 기준으로 이미지 병목인지 텍스트 렌더 병목인지 분류
> `unused CSS/JS`는 전역 청크 구조인지 페이지 전용 코드인지 구분
> 낮은 위험 작업부터 우선순위를 제시

### 11-2. 구현 요청 템플릿

> 전역 Provider, 인증 흐름, 전역 네비게이션은 마지막 단계까지 건드리지 않음
> 먼저 이미지, 전역 CSS의 페이지 전용 규칙, 비핵심 클라이언트 슬롯 분리부터 진행
> 수정 후 타입체크와 관련 E2E 실행
> 변경 의도, 영향 범위, 남은 리스크를 함께 정리

## 12. 절대 금지 체크리스트

- attribution 없이 LCP 원인 단정
- 점수만 보고 구조 리팩토링 시작
- `unused CSS` 수치만 보고 Tailwind 전역 구조 개편
- `unused JS` 수치만 보고 Provider 범위 변경
- 전역 레이아웃 수정 후 E2E 생략
- 모바일 확인 없이 성능 개선 완료 처리

## 13. 이 문서를 적용해야 하는 상황

- Next.js App Router 프로젝트 시작 시
- 홈/랜딩/프리뷰/상세 첫 화면 성능 개선 시
- Lighthouse 점수 하락 원인 분석 시
- AI에게 성능 최적화 작업을 위임할 때
